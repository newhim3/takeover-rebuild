# 加载与地图边缘修正（r11）

本轮只修改资源交付、缓存、预热和地图显示。敌军决策、难度、兵种规则与法术规则保持不变，没有接入补充游戏的源码。

## 实际找到的瓶颈

公网首次标题页原先发出 65 个请求。采样中，一些只有几 KB 的脚本等待了约 10.8 秒；这部分主要是公网入口的请求延迟。战场另有 81 个请求。合并后的第一轮采样分别减少到 16 和 32 个请求，仍有网络等待。

| 公网样本 | 修改前 | 第一轮合并后 |
| --- | ---: | ---: |
| 首次标题页采样结束 | 16.47 秒 | 11.14 秒 |
| 暂停战场采样结束 | 13.49 秒 | 9.91 秒 |
| 再次进入已访问的关卡选择页 | 11 毫秒 | 9 毫秒 |

这些时间包含等待图片解码及网络空闲，不能当作完整实玩帧率或所有玩家的等待时间。原始记录在 `loading-profile/before-public.json`、`after-public.json`。后续持久缓存和预热完成后，没有再反复跑整套公网战役采样。

## 完成的交付修改

- 原有脚本按原顺序合并为 `game-shell.js`，8 个样式表合并为 `game-shell.css`，保留源文件可编辑性。内容哈希用于自动更新版本。
- 原图打成 86 个兵种/建筑包和 25 个地图包；没有缩小、重画或有损压缩原 PNG。1,522 个包内条目与对应源文件逐字节一致；其中新增边缘遮罩明确是修补产物。
- HTTPS 公网及本机 localhost 启用持久资源缓存。联机 API、指令和 WebSocket 不走静态缓存。普通局域网 HTTP 受浏览器安全环境限制，使用 HTTP 缓存。
- 有缓存时，首页请求最多等 500 毫秒再显示缓存页面，后台继续取得更新；首次未缓存仍依赖网络。
- 提前加载下一页菜单；选中关卡信息后加载该地图。当前可见建筑先于全部动作方向预热。
- 不同地图共用原地形图片对象，避免对相同素材重复解码。全部地图只有 55 张不同位图，估算解码像素约 9.84 MiB；这是地形位图估算，不是整个游戏的内存占用。
- 菜单覆盖时隐藏战场 HUD 图层，原 UI 外观和操作位置保留。

最终定点检查关闭普通浏览器缓存：标题页重复导航约 39.4 毫秒；原图和脚本通过资源缓存返回，服务器收到零个静态资源请求。服务端仍收到两次 `/api/network` 读取，证明实时接口没有被缓存。第 7、17 关同时加载完成，共用 48 个地形图片对象，没有页面脚本错误。记录：`loading-profile/r11-cache-check.json`。

## 矩形边缘的两个原因

1. 原第 7、17、24 关共用的导出遮罩 `shape5495` 在 800×600 边界形成水平切边。现保留中央原遮罩，依据原悬崖图层支撑重建边缘遮罩。这是修补出的遮罩，不冒充原版完整遮罩；没有生成新地形或修改道路、据点及国家地形帧。
2. 战场画布维持原逻辑坐标比例，宽屏两侧留白颜色与画布内天空不同，露出竖直色带。现在两者使用相同天空色，不拉伸地图。

节点、建筑位和道路采样保持可见：第 7 关 868 点，第 17、24 关各 872 点。其余地图的原遮罩没有替换。第 7 关两次读取只绘制一次原地图底层；装饰物仍独立排序。

最终暂停预览：`loading-profile/r11-paused-level7.png`。检查限于资源、语法和静态显示；没有声称所有国家所有战斗情况已实玩验证。

## 后续编辑注意

改脚本和样式后运行 `node delivery-build.cjs`。交付顺序以 `delivery-manifest.json` 为准，不直接改生成的 `game-shell.js/css`。

改地图导出或 PNG 后：先运行 `tools/restore-native-maps.py`，再运行 `node tools/build-asset-packs.cjs`，最后运行 `node delivery-build.cjs`。重建地图会重置包版本，必须再打包。修改原 UI 位图后也应更新其资源版本，避免旧资源被持久缓存。

最终服务器更新为 r11b，本地首页、版本脚本及资源缓存文件均返回 200，内容版本对应当前源文件。旧 Cloudflare 进程在最终核对时已经退出，旧域名无法解析，已重新启动临时入口；当前地址以 `.tools/network/public-address.json` 为准。重启后已有房间需要重新创建。
