# 补充源码与当前项目的改进方向

本次只分析与记录，没有接入补充源码，没有修改游戏运行代码，也没有重启服务。优先范围仍是操作流畅和原版画面协调。

## 资料边界

主要阅读 `reference/supplement-20261006/web/takeover.js`。这是 Haxe 4.0.2 编译输出，包含 OpenFL/Lime、游戏逻辑和第三方作者改动，不是独立的原始 Haxe 工程。文件开头将联机、黑暗帝国等列为 TODO，不能据此认为这些功能已有完成的可替换实现。APK 中的混淆代码只作为补充参考，不执行、不安装。

## 1. 加载：按场景管理图集，提前准备实际会用到的动作

参考源码：`GameVisualManager.processAtlasManagerBlock`（7515 行）、`startLoadAtlas`（7545 行附近）、`GameAtlas.processLoading`（6150 行附近）。它明确区分当前场景需要哪些图集、哪些已经存在以及哪些可以释放；图片就绪后建立 Tileset，再载入动画描述。

当前项目：`game.js` 的 `images` 保留每个动画文件对应的 Image，未设置战场图片内存预算；`preload()` 预加载走动方向和向下攻击，其余攻击方向仍可能到首次使用时请求。菜单已经有 64 MiB 的估算保留预算，不能把已经完成的菜单缓存当作尚未实现。

建议：继续使用现有原画，按“国家、兵种、场景”组织适当大小的图集；下一场实际会出现的动作先异步解码。近期场景和正在显示的素材保留，其他素材按内存预算释放。不要一次加载全部国家和所有动画，也不要盲目合成一张超大图集。

收益判断：有望减少临战首次转向/攻击时的加载抖动及跨关卡内存增长；准确耗时仍需一次短性能采样确认下载、解码、纹理上传分别占多少。

## 2. 原版观感：恢复装饰物与部队的遮挡关系

参考源码：`level_LevelLand.updateLandObjectsView`（40883 行附近）区分 `mcArea`、`mcRoads` 和 `mcObjects`。装饰物保留自己的世界位置，通过 `level_LevelLandObject.render`（41002 行）进入世界绘制层；树木、山石等不只是一张平面背景。

当前项目：原地图脚本把地面、道路及装饰一起绘制进 `terrainWorld`。`game.js.draw()` 随后按 y 排序建筑、部队、宝箱与建筑位，地图装饰不参与这个排序。因此部队经过树木背后时，现有绘制结构仍会把部队画在树木之上。这里是代码层面的明确差异，尚未在浏览器逐个地形实拍验收。

建议：缓存地面与道路，将原 `mcObjects` 的图形、国家帧和原坐标单独保留，并按脚底/基座位置与部队、建筑共同排序。特效继续分为地面、物体之间及上方，不更换贴图或地图布局。先完成第 7 关的几处树木/山石遮挡，确认之后再扩展。

## 3. 操作：明确永久命令与临时接敌的状态边界

参考源码：`battle_squad_Squad.updateNewFSM`、`processFSMRules`（17300 行附近）、`resetCurrentTarget`（17739 行）。行军、战斗、等待、入堡等有明确的转换入口，并区分目的地、当前事件及交战目标。

当前项目：已有 `OrderRuntime.tick()` 统一处理顺序及 r9 手动行军规则，但守城、接敌、追击、入堡和目标转换仍会修改同一组 `order/path/pathTarget/combatTarget` 字段。近期几次改令问题，说明这些字段的修改边界值得进一步整理。

建议：保留现有战斗规则，给每条新命令版本号；长期目的地由指令入口维护，接敌只设置临时目标。临时交战结束时，仅在版本号未变的情况下恢复原命令；入堡、死亡或所有权改变集中清理状态。采用明确的进入/退出处理，减少分支互相覆盖，不整套照搬另一游戏的 AI。

## 4. 联机：真正区分首次完整同步和后续变化

当前证据：`multiplayer-server.cjs.snapshot(r, full=false)`（10 行）声明了 `full`，但函数体未使用它。每次仍重建并发送 `definitions`、国家条令、设置、建筑、建筑位、宝箱和人类部队完整路径。`r.unitDefinitions` 也没有承担定义发送版本的记录工作。服务器已有 WebSocket 压缩，不能说它完全没有压缩。

一次离线构造检查：24 支玩家部队发出行军指令，加上地图自带 3 个食人魔，共 27 个单位；未推进战斗或启动房间。快照 JSON 为 22,935 字节，其中兵种定义 5,081 字节，人类路径数组 2,854 字节。除序号和时间戳外，`full=true` 与 `full=false` 的输出相同。这是未压缩构造数据，不是公网带宽或延迟实测。

建议：首次加入、重连及周期校验发送完整状态；兵种定义/条令按版本更新，路径按命令版本更新；常规同步只发变化字段和新增/移除对象。变化包必须引用可验证的基准序号，基准缺失时请求完整状态，防止优化造成“少发之后两边状态不同”。经济、血量、归属和伤害继续由服务端唯一计算。

客户端位置缓冲已经实现 110–300 ms 的自适应延迟。它换取平滑，也会增加观察延迟；应分别记录 RTT、抖动、处理耗时和缓冲延迟，再决定稳定局域网的缓冲范围，不能直接把缓冲改成零。

## 5. 时间与计算：避免一次昂贵任务阻塞整场

当前项目：服务端每 50 ms 回调推进固定 0.05 秒，没有累计实际经过时间。单机用渲染帧时间推进逻辑，每段最多 0.04 秒；这与服务端的时间划分不同。AI 决策仍会做较多路径评估、排序及战力计算。地形缓存已解决镜头移动重绘，但首次生成和占领后的重建仍在主线程调用 `native.draw()` 与 `getImageData()`，存在同步耗时。

建议：单机与服务端使用同一固定逻辑步长和带上限的时间累计；渲染独立插值。服务器不能无限补算卡住的一段时间，恢复窗口、后台暂停与房主调速需要明确规则。把 AI 各国决策错开到不同步骤，复用单次决策的战场摘要和路径评估；地形按地区预生成/重建，必要时再将能够分离的绘制任务移到 Worker。先测耗时，再决定是否值得引入更多并发与维护复杂度。

## 实施优先顺序

1. 一次短采样建立基线：冷进入、重复进入菜单、常见兵量下移动、联机命令确认。只采样关键场景，不重复长战役。
2. 完整/变化同步和动作素材就绪管理：分别处理联机重复数据、首次动作抖动。
3. 第 7 关装饰物遮挡：用原坐标和原图层改善画面协调。
4. 指令状态边界、统一逻辑时间与错开 AI 决策：逐处改善停步和命令覆盖，保留已认可的机制与数值。

以上是从源码确认的结构差异和待测的性能方向，不是已经实施或已测得的 FPS 提升结果。
